# IQ archive and restoration: proposed protocol, not production support

Basis: PR #47 `d90b17338eba5eacb436eaff161c3c416fd23380` (checked remote 2026-11-13); preserve existing `ISSUE_ARCHIVE_UNSUPPORTED` guard. This proposal is a design target, not an allocated `.mcase` version, and cannot be treated as current API or acceptance.

## Scope and evidence completeness

A full-case archive needs an explicitly negotiated new outer `.mcase` version and a required IQ profile, canonical manifest entries and digests. Current parser/consumers must reject it rather than quietly ignoring unknown required components. IQ inventory must include all issue snapshots, *all* ordered events and receipts, source case identity, source policies/provenance, and evidence version inventory over **all** events, not just current state. Include every referenced version's original content bytes and complete, independently validated descriptor and custody/provenance available at that time. Same evidence ID with two hashes represents two different versions, not a lookup by ID. Evidence may have been registered with a hash alone (no bytes); older bytes may have been overwritten or removed. Missing, inaccessible, unverifiable, unauthorized, or ambiguous original bytes/descriptor -> reject full export; never substitute current content, synthesize metadata or silently drop the historical version. A metadata-only export, if ever built, must be a separate, explicitly incomplete profile and must not enable full-case restore or replace this guard.

Replaying each event from Create must reproduce the exact current snapshot and frozen packets. Every event needs exactly one matching immutable receipt and vice versa. Check event sequence continuity, per-issue revision, role/actor, response, and reconstructible request digests. In IQ-1A Create, the event saves sorted references while its receipt hashes the original body, so the original ordering can be lost. Preserve Create digest as opaque provenance, not proof of a reconstructed request; no cryptographic or original-input verification claim. Append digest can be reconstructed from stored payload, issue ID, request ID and prior revision; preserve all digests and IDs unchanged. Hashes detect inconsistency, not adversarial forgery or actor identity authenticity.

Export must authorize full case and every historical evidence version, hold a consistent database snapshot coordinated with content storage, and validate bytes against their exact hashes. Blob lifecycle must prevent concurrent mutation/deletion during snapshot, including work outside the process-local lock. Recheck policy if it can change while assembling. Strict bounded parsing: total compressed/uncompressed sizes and file count, byte/depth/node/string and evidence budgets, duplicate JSON keys and ZIP paths, normalized paths, no symlink/traversal, exact numeric types, nonfinite values, unsupported versions, unknown required members and reference mismatch. Fail closed and avoid disclosing whether a restricted source exists. Recheck complete final manifest and bytes, not only preflight. Legacy and working-record export routes remain protected.

## Restoring into a new destination only

Authorize the actor to create a destination and to receive the full source data before existence, detailed errors or content are disclosed. An imported archive cannot establish the authenticity of its own ACL or source classification; apply destination policy no weaker than source where independently verified, otherwise require a conservative restrictive policy or reject. Audit the import as a new action, without rewriting original actor, timestamps, event body or origin ID. Do not overwrite/merge a case. Allocate destination identity atomically and record a separate immutable origin/destination mapping; avoid modifying original event/receipt content. Read paths must use the mapping explicitly. Validate archive, whole-case relationships and all referenced blobs before any visible state. Unknown/legacy/mixed profiles or orphaned issue/event/receipt sets must be rejected, not salvaged.

### Cross-resource atomicity proposal

A SQL transaction alone cannot roll back filesystem operations. This requires storage and access changes not present in PR #47:

1. Generate an unguessable import transaction ID; reserve destination in a transaction with a unique constraint and a non-visible `PREPARING` state. Reserve uniqueness at database level across processes. No list/get/download/search/background worker may expose or process it; inventory every path and enforce a shared case visibility gate. The current application is not shown to enforce this, so this is a required implementation gate.
2. Stream files into a private same-filesystem staging directory with path-safe no-follow/exclusive operations; enforce budgets, hash original bytes, revalidate full graph and policies. Write immutable, content-addressed objects via exclusive create/no replacement. Verify collision bytes, restrict permissions. Flush file contents and parent directories and check errors. Never trust ZIP names as OS paths. A deployment must explicitly establish its filesystem's rename/fsync/durability guarantees; this protocol is invalid where those are not provided.
3. Before any DB reference can become visible, durably promote each staged object to its final immutable object-store location. Existing identical objects can be reused only after verification. A lease/transaction marker roots promoted-but-not-yet-committed objects against garbage collection; GC must be coordinated across processes. Orphans after a crash are acceptable; partially visible cases are not.
4. In a single DB transaction, recheck destination reservation, authorization, source mappings, all object references and generation/tombstones; write whole-case data, all IQ rows and mappings, and set a single visibility marker `READY`. Commit only after referenced blobs are durable. Readers consult marker within their own transaction before reading. If commit fails or process dies before commit, destination is not visible. If commit succeeds, all referenced bytes were already durable; no later rename is necessary for availability. Record import idempotency result atomically so retries cannot duplicate a case.
5. Recovery reconciles reservations/leases idempotently: non-committed imports are aborted and staged or orphan objects collected only after grace and no references/leases. For `READY`, verify all object references before service or fail case closed and raise an operational alarm. Protect against races with GC. A durable commit followed by a lost response returns the same import receipt, not a second case. At no point may a reader see a half-restored case or an exported partial case.

This requires case-path-to-content-address indirection, a complete visibility gate, cross-process lock/lease, crash testing on supported filesystems, lifecycle migration and whole-case atomicity, not just the IQ tables. Alternative implementations need equivalent externally observable properties. Staging itself is not an atomic restore.

## Idempotency and archival receipt isolation

Archive receipts remain immutable archival facts associated with *source* case/generation. They are not active destination receipts. A new destination gets a random fresh mutation generation; record imported original `(source generation, case, operator, role, requestId)` separately from active receipt storage. On writes in the new generation, reject every imported request ID (conservatively across operators and roles) rather than replaying old responses or allowing a collision; maintain a unique tombstone/index for all historic IDs. Retain tombstones across re-export and subsequent restores, merge them with imported tombstones, and bind destination writes to destination ID + active generation. Both request ID check and new event/state/receipt insert must be in the same serialized database transaction. Detect malformed/duplicate archived IDs and refuse restore; do not rewrite the immutable historic receipts or expose old response bodies via active idempotency lookup. A generation must never be inferred from client-provided untrusted data. Define bounded storage and resource handling without truncation.

## Acceptance gates

Independent tests need: multiple issues and >50 events; multiple hypotheses and version revisions, all rounds and frozen packets; exact same-ID/different-hash historical content including hash-only registration and missing/changed/restricted historical version; orphan/duplicate/corrupt records; strict parser abuse and resource budgets; old request ID collision/replay across operators, roles, and multiple generations; authorized/unauthorized source and destination policies; import retries and concurrent create/export/restore/GC; injected crashes before and after each file sync/promotion/DB commit; restart recovery and no visible partial destination; full re-export then re-import preserving origin and tombstones; and integration with all legacy/working-record paths and actual supported browser UI. Independent review and production-scale/CI tests remain required. No merge/deploy before those gates.

## Research code limitations

`archive_candidate.py` is a bounded JSON research preflight, not a `.mcase` parser, archive writer, authorization or restore mechanism; it rejects missing/surplus evidence, but its small descriptor is not a validated production evidence schema, its JSON/byte limits are artificial and it does not ensure outer-case or filesystem safety. `validate.py` replays IQ state but cannot establish authenticity of self-supplied archive contents or historical bytes as originally recorded. Both require callers to establish authorization before parsing or disclosure. Synthetic local tests do not qualify as production acceptance.

### Independent preflight review follow-up

The toy preflight now only accepts the two IQ-1A role labels, rejects extra fields in its deliberately incomplete reference-key descriptor, and rejects request IDs repeated across operators/roles. The actual live IQ-1A model allows such repeated IDs; the stricter candidate rejects those legitimate histories rather than transforming or dropping data. A production design must decide how to faithfully preserve and tombstone these cases before lifting the guard. These checks do not establish actor authentication or historical authorization, descriptor completeness, nor actual generation/tombstone behavior.
