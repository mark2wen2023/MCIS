# W7.3 candidate: read-only contract and transaction review

No implementation or tests changed/executed for this candidate. Recommendation: split clear domain-validation parity from the broader concurrency/lock-order question; do not declare five-endpoint outer-lock patch safe without cross-route evidence.

## Clear domain rules
C# Consultation.OpenRound (Consultation.cs:276 onward) rejects IsNullOrWhiteSpace draftVersion/operator, null or whitespace partyId, and duplicate PartyId using StringComparer.Ordinal. It does not trim valid IDs or names: PartyId="A" and " A " are distinct; "A" and "a" are distinct. Nonblank values must retain their exact strings for storage, lookup and audit. ConsultationParty constructor merely substitutes empty for null; name has no nonblank validation. Do not add name-nonempty rules just because the UI requires them. WaiveReply rejects whitespace reason/operator but retains valid reason contents. Python's RoundIn currently has unconstrained strings and only parties min_length1; WaiveIn reason min_length1 still permits whitespace. These are clear targeted parity gaps. Python whitespace helpers and .NET IsNullOrWhiteSpace differ for some Unicode control characters; if claiming exact parity, characterize those explicitly instead of silently broadening rejection.

Schema identifies alignment with C# and retains partyId/name as strings without uniqueness constraints; OpenAPI consultation summaries establish lifecycle rules but do not specify detailed request-body validators. CONTRACTS.md §consultation states only one reply OR waiver per party, one decision per comment, prior close required before open and all-replied OR deadline close. Domain C# supplies the precise missing input rules. No separate DEFECTS/W7.md was available locally or via repository lookup(404); do not invent an additional architecture ruling. Validation errors should preserve the established domain/API error style and append neither state nor audit. No permission/default-deadline changes are justified by this patch.

## Lock lifetime and blocking risk
Database.session yields a Session, commits after the route body, rolls back on exceptions and finally closes. An intended outer WRITE_LOCK must remain held through commit/rollback, not only through state mutation or audit.append. `with WRITE_LOCK, ctx.db.session() as s` has the desired exit ordering for participating transactions; RLock permits nested audit.append on that same thread. Reversing nesting or releasing before context exit is insufficient.

However, the service is NOT uniformly ordered. recommendations._move calls put_doc (flush obtains SQLite writer) before audit.append (acquires global WRITE_LOCK). Existing other routes similarly do not hold the global lock for their entire transaction. A new consultation route acquiring WRITE_LOCK before SQLite writing can invert that order:
1. A(non-outer-locked route) flushes and holds SQLite writer, paused before audit.append.
2. B(new consultation outer lock) acquires WRITE_LOCK, then waits for SQLite writer during flush.
3. A resumes and waits for WRITE_LOCK. Neither can commit while waiting. SQLite busy timeout normally breaks the cycle with OperationalError/500 and rollback, so do not describe this as guaranteed infinite deadlock; it is still an invalid concurrency guarantee and availability failure.
This can cross case boundaries because SQLite serializes writers at the database-file level. Existing reports use outer locks already, but precedent does not eliminate the inversion. A complete consistent transaction-entry ordering, transaction strategy or explicit retry/rollback design needs broader review and authorization; do not silently retrofit all routes within this UI follow-up. A consultation-only lock cannot be advertised as making unrelated audit writers safe. Raw imports/other session entry points must also be considered before claiming global serialization.

## Proposed independent reproducible verification
1. Per-test fresh temporary SQLite database, single service process, multiple real HTTP clients synchronized before requests. Repeat simultaneous open attempts: exactly one201 and one409, one new round, one open event, valid audit chain, no500. Run duplicates for same-party reply vs reply, reply vs waiver, same-comment conflicting decisions, close vs reply/waiver and different-party updates. Verify successful writes retained(no lost JSON updates), failed attempts add no audit, and sequential keys/chain.
2. Deterministic test-only interleaving via Events/instrumented wrappers, not production sleeps: pause an actual recommendation transition immediately after its real put_doc flush; start consultation request and signal when it has acquired the outer lock; then release A to call real audit.append. Use bounded waits and record each phase/status. Do NOT put a two-party Barrier inside a correctly serialized lock (that would manufacture a test deadlock). Preserve initial red failure/timeout evidence; ensure teardown always releases events. Repeat with a different case on the same DB file.
3. Commit-boundary test: hold first request just before real commit while launching second; second must not read stale eligibility before first commit if the chosen design promises serialization. Include forced audit/commit failure rollback checks with no orphan state or events.
4. Validation table: blank/space/tab/newline draftVersion and partyId; exact duplicate vs case-distinct vs leading/trailing-space-distinct IDs; valid values preserved byte-for-byte; empty name allowed; whitespace reason rejected; nonblank reason untrimmed. Distinguish domain validation failures from malformed JSON/Pydantic failures. Cover RO/Deny and case isolation.

## Multi-process boundary
threading.RLock protects only threads in one interpreter. Two uvicorn workers/independent service processes do not share it. SQLite unique constraints prevent some duplicate keys but do not by themselves enforce the one-open-round predicate, prevent lost JSON updates, or ensure audit seq/prev atomicity. A passing single-process test must explicitly retain the single-process deployment assumption. Multi-process/host support would require a separately designed database transaction/concurrency protocol; it is not established by these locks.

The lock-inversion scenario above is a **source-based finding, not an executed reproducer**; the proposed deterministic interleaving tests were not run. Retain it as an unresolved cross-route risk requiring a separate design/review.
