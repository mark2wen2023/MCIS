# Report output bundle v1 — explicit local download, contract candidate

## 1. Scope and exclusions

An explicit user action generates ONE PDF OR ONE DOCX and offers one ZIP download containing those exact newly generated bytes, the full stored report document used as renderer input, and an associated export audit record. It is NOT `.mcase`, an import format, a server-retained original, a backup of all evidence, a publication, a signature, an authenticated identity or a professional finding. No new persistent table, stored rendition blob, receipt, import path, package version or change to working-record archive is introduced. W7's proposed1.4 allocation is unaffected. Existing ordinary PDF/DOCX export remains unchanged.

Only the existing `report.export` event and its existing ReportAuditRow operation snapshot are persisted. Neither the ZIP nor the PDF/DOCX nor this full rendering-input snapshot is stored by this operation. Subsequent report edits cannot recover these downloaded bytes from that audit hash. Regeneration is a new export, never retrieval of a lost original. The caller must preserve the ZIP if wanted. Success means the server committed an export record and prepared a response, NOT that a browser saved a complete file.

## 2. API and explicit action

New GET `/api/v1/cases/{case_id}/reports/{report_id}/output-bundle:preview`, under the same full report/audit/source gate and short reserved transaction, returns exactly `{caseId,reportId,reportDocumentSha256,reportVersion,reportStatus,storedLanguage,canonicalization:'MCIS-PY-JSON-1'}`. It returns no raw source, renders nothing and appends no audit. Preview applies the same strict stored-report schema, Unicode/depth/finite-number validation and2MiB canonical-byte budget as POST before producing its digest; it is not an unbounded full-document serialization endpoint. Digest covers the canonical full current stored report doc. UI displays version/status/language and explicitly identifies the currently saved snapshot, not unsaved editor content. Permission/version changes require a fresh preview and user choice, not an automatic new POST. The preview is not authorization for future access.

New POST `/api/v1/cases/{case_id}/reports/{report_id}/output-bundle`.

Content-Type must be `application/json`, optionally with the sole standard `charset=utf-8` parameter (case-insensitive; whitespace around semicolon allowed, parameter exactly unquoted `charset=utf-8`). Other encodings, quoted variants or parameters reject415; bytes are always strict UTF8. Exact body `{format: 'pdf'|'docx', lang: 'zh'|'en'|'bilingual', expectedReportDigest: '<lowercase hex64>'}`. All three fields required; no default language, extra fields, client paths, client report document, source URLs, arbitrary renderer options or automatic both-format mode. Body UTF8 <=1024 bytes, strict JSON object without duplicate keys, non-finite numbers, invalid Unicode/surrogates or BOM. No external fetching, LLM call or upload.

The UI presents an explicit single-format choice and a separate “生成可追溯下载包 / Generate traceable download bundle” action. It must say this is user-local download only, no server original retention. One intentional request renders exactly once; no automatic POST retry, including after timeout,401/403,409,5xx, malformed ZIP, hash mismatch or browser download failure. A lost response is an unknown delivery outcome; a new explicit user generation may create a second audit event and different bytes. No UUID or audit seq is represented as an idempotency receipt. Pending/unknown UI metadata binds case,report,role/operator,format,language and expected digest; a reload retains only that metadata, not report text or bytes. Unknown state cannot be resolved by a fabricated recovery GET or by an audit count. After manually checking local downloads, the user may explicitly abandon that delivery attempt and choose NEW generation with a fresh preview; UI warns this may create an additional export event and different bytes. No automatic retry of the old request is presented as recovery.

## 3. Authorization and linearization

Both phases use the existing local-role-header identity model. Only Investigator/LeadInvestigator satisfying existing full-report content gate: all12 categories explicit ReadOnly/ReadWrite and no applicable field rule, including complete `audit` permission. `report_draft` ReadOnly is sufficient because this reads content plus an ordinary access/export audit, not a document edit. No role/policy changes or automatic permission elevation. Default Investigator remains denied. Full gate precedes case/report existence disclosure, parsing stored report or rendering. This endpoint ADDS a conservative current-case source gate by explicitly calling `working_records_archive.full_access` at preview and both POST phases; the ordinary report check_access/get_report does not itself perform these per-source checks. Validate every existing EvidenceRow/InterviewRow document's caseId and evidenceId/recordId against its same-case row key before using it. Existing protect_interview/protect_source checks cover current confidentiality, missing bound evidence and mismatched registered source hash; propagate their403/409 refusals without source details. This examines ALL currently stored same-case evidence and interviews, not only report citations, and can refuse an otherwise readable report because another current source is inaccessible. It is not a complete report-citation dependency-closure validator, raw-source byte/hash verification or proof of original source authenticity. Historical missing/unregistered citations in saved report text are preserved as stored and not promoted; referenced sources that no longer exist are not promised obtainable. No source bytes are included. Source content changes alone do not invalidate a saved report snapshot: repeat current access/binding checks in phase2, but do NOT require source document fingerprints to remain equal. Report/policy fingerprints still must match.

Phase1: a short `WRITE_LOCK -> BEGIN IMMEDIATE` transaction runs current report availability and full-content/source checks, obtains a detached deep copy of the exact stored ReportRow.doc, and captures report and policy fingerprints. Before rendering, compare canonical full report doc SHA to expectedReportDigest; mismatch is409 REPORT_OUTPUT_CHANGED, with no renderer call. Close transaction and release lock before rendering. No audit is appended here. Render once outside any SQLite transaction or application WRITE_LOCK, using that detached report and requested language. Never mutate report.doc.lang to the requested rendering language. Freeze report.json canonical bytes before rendering and pass a separate deep copy to the renderer, so a renderer mutation cannot silently alter the captured document or digest.

Phase2: another short `WRITE_LOCK -> BEGIN IMMEDIATE` transaction repeats authorization, availability and source checks; reload report/policy and compare fingerprints before adding any event. If access changed to deny,403. If access remains allowed but fingerprints differ,409 `REPORT_OUTPUT_CHANGED`. No stale output is returned. No mutation is applied to report or policy. Append exactly ONE existing `report.export` operation, read its exact persisted audit row line and operation snapshot within the transaction, construct and validate final ZIP, then commit. Any preparation/size/hash/validation/serialization failure before commit rolls back the export event and snapshot. The response bytes are released only after successful commit.

Rendering outside the transaction permits concurrent policy updates. The second authorization transaction is the delivery authorization linearization point: a revocation committed after it cannot recall already authorized/transmitted bytes. No claim of instantaneous revocation or background cancellation. ZIP assembly remains bounded inside phase2; it must not invoke the renderer again. SQLite locks may briefly block other writers; no claim all unrelated routes are multiprocess-safe.

Report fingerprint: SHA256 of canonical `{caseId,reportId,createdUtc,updatedUtc,doc}` with original DocMixin UTC strings and full doc, not merely report status or section count. Policy fingerprint: SHA256 of canonical `{source:'default'|'saved',createdUtc:string|null,updatedUtc:string|null,doc:<entire effective policy>}`. Default has null timestamps. Saved policy includes its original row timestamps and full document. Fingerprints stay server-side; manifest does not disclose policy. Equality is snapshot equality, not a durable monotonic version: an externally performed exact ABA restoration is not detected or claimed detectable. No timestamp-based reconstruction of prior access. Ordinary new API policy writes changing timestamps or content are detected.

## 4. Exactly four ZIP members

No directories, user filenames or optional extra entries:

1. `report.pdf` OR `report.docx`, selected by request. Original bytes returned by that single renderer invocation, never reserialized/re-rendered to compute a hash.
2. `report.json`: canonical encoding of the full detached stored report doc used as input, preserving every existing field/value/array order/string. It is not the original database JSON storage whitespace or a claim of original author file bytes.
3. `audit.json`: canonical envelope containing the exact original audit line string and original operation snapshot, defined below.
4. `manifest.json`: canonical JSON exactly defined below.

ZIP method ZIP_STORED (method0), fixed member order (rendered file, report.json, audit.json, manifest.json); all names fixed ASCII. General-purpose flags0; creator system0, creator/extractor version20, internal attributes0, external attributes0x20 (regular DOS archive file). DOS date1980-01-01 (date33), time00:00:00 (time0). No comments, extra fields, encryption, symlinks, ZIP64, data descriptors or multidisk records. Each local header is followed immediately by its member bytes; local entries start at offset0 and are contiguous in the prescribed order. The four central-directory entries immediately follow all local records; their CRC32, compressed/uncompressed size, name, method, flags, version and DOS timestamps match the local entry, and offsets identify those exact starts. Each member size equals both its compressed/uncompressed sizes; CRC32 is recomputed over actual bytes. The EOCD follows the central directory immediately and ends exactly at EOF, count4 on disk0 with matching directory offset/length and zero comment. No prepended/trailing/gap bytes, duplicate entry, alternative names or unrelated archive records. No metadata copied from user input. These binary constants are a protocol, not merely zipfile defaults; implementation must explicitly set them and assert its emitted bytes match. Content is not deterministic: PDF metadata or DOCX packaging and the new audit event may change per invocation. Repeated exports are not expected to have equal hashes.

Canonical encoding `MCIS-PY-JSON-1`: UTF8, no BOM/trailing newline, JSON object keys sorted, separators `,` and `:`, ensure_ascii=False, allow_nan=False; arrays and string contents unchanged. Finite JSON numbers retain Python JSON serialization semantics, including1.0 versus1; this is not RFC8785/JCS. Consumers hash the exact report.json bytes, not a JavaScript parse/stringify reconstruction. Reject non-finite/unrepresentable input instead of coercion. JSON nesting max64, counting root container as depth1.

## 5. Exact manifest and audit association

Manifest exact keys:

```
{
  "format": "MCIS-REPORT-OUTPUT-BUNDLE",
  "version": 1,
  "caseId": "<current case>",
  "reportId": "<stored report id>",
  "outputFormat": "pdf|docx",
  "language": "zh|en|bilingual",
  "canonicalization": "MCIS-PY-JSON-1",
  "members": [
    {"name":"report.pdf|report.docx","mediaType":"application/pdf|application/vnd.openxmlformats-officedocument.wordprocessingml.document","byteLength":123,"sha256":"<lowercase hex64>"},
    {"name":"report.json","mediaType":"application/json","byteLength":123,"sha256":"<lowercase hex64>"},
    {"name":"audit.json","mediaType":"application/json","byteLength":123,"sha256":"<lowercase hex64>"}
  ],
  "identityMode":"local-role-header-unverified",
  "retention":"client-download-only",
  "sourceScope":"stored-report-document-not-source-originals"
}
```

The `audit.json` envelope is exactly:

```
{
    "seq": 123,
    "line": "<exact original AuditEventRow.line, not reserialized JSON>",
    "lineSha256": "<SHA256 of UTF8 line, NO added LF>",
    "snapshot": {
      "key":"RA-...",
      "createdUtc":"<original row UTC string>",
      "updatedUtc":"<original row UTC string>",
      "doc": {
        "reportId":"...","sectionId":null,"sentenceId":null,
        "reason":"<canonical binding JSON below>","beforeValue":{"status":"<original report status>"},
        "afterValue":{"format":"pdf|docx","lang":"zh|en|bilingual","sha256":"<rendered file SHA>"},
        "summary":"<existing append_operation summary>","auditSeq":123
      }
    }
  }
```

Numeric lengths/seq/version are integers, not booleans. Manifest has no self-hash: response X-Sha256 hashes the complete ZIP. The `members` array covers the other THREE members only, without circular digest claims. Read actual audit seq/line/snapshot after append; never synthesize a line from parsed fields or infer a neighboring seq. Snapshot key must match line `snapshot_ref = report-snapshot:<key>`; server loads both AuditEventRow and ReportAuditRow using the exact current case_id, and verifies category Report/action report.export, entity_type report and entity_id/reportId. The original audit line and snapshot.doc have NO case_id/caseId field: do not add or require one. Within the bundle, case binding is transitive through reason.reportDocumentSha256 -> exact report.json bytes -> report.json.caseId/reportId, plus line.entity_id and snapshot.doc.reportId matching that report. It is not a direct case field in the original line. Snapshot.auditSeq equals line.seq and audit.json seq. Original actor/role and time are self-reported operational history, not verified identity.

For this new endpoint only, the existing free-form reason string is canonical JSON with EXACT keys `{bundleFormat:'MCIS-REPORT-OUTPUT-BUNDLE',bundleVersion:1,reportDocumentSha256:<report.json SHA>,format:<pdf|docx>,lang:<requested language>,documentSha256:<rendered bytes SHA>}`. Pass this string to append_operation; original audit.line and operation snapshot must carry the identical reason. This binds the report.json and rendered member hashes into the preserved original audit line, rather than only declaring their association in the unsigned manifest. Old export reasons are unchanged.

Existing append_operation before/after contract stays unchanged: before exactly status, after exactly format/lang/rendered-file-sha. Audit line before/after are existing textual summaries; full afterValue is in the included operation snapshot. Do not add fields to the legacy action snapshot/schema or put a ZIP hash inside the ZIP (circularity). The report.json hash is bound only through existing reason text as specified above. Verify supplied report.json reportId/caseId/status against the manifest and included beforeValue; rendered-file SHA equals snapshot.afterValue.sha256 and manifest member SHA. This is an explicit package association, NOT a cryptographic proof that arbitrary imported bytes were rendered from arbitrary report.json. There is no import/verification service accepting this package as trusted content.

A single audit line includes prev hash but not preceding chain lines: it cannot verify the entire database chain or prove that any server ever committed the event. SHA values only verify byte self-consistency in this unsigned package; an editor can change all members and hashes. No signature, authenticity, certification, public-register or complete source provenance claim.

## 6. Budgets, errors and response

Fixed engineering caps, never truncate: report.json <=2MiB; rendered file <=16MiB; audit.json <=256KiB; manifest.json <=16KiB; complete ZIP <=19MiB; exactly4 members. The2MiB report budget is checked before renderer; final renderer bytes cap before phase2; audit/manifest/ZIP caps inside phase2 with rollback. These are serialized input/output caps, not a hard renderer CPU/RSS sandbox; rendering can allocate intermediate data before its output-size check. New handler validates canonical serialization and known report schema before invoking renderer. Large/invalid stored report is refused, not silently edited. These limits affect only this new endpoint, not old report editing or existing export.

415 `REPORT_OUTPUT_MEDIA` non-JSON request;422 `REPORT_OUTPUT_INVALID` body or stored-report invalid;413 `REPORT_OUTPUT_BUDGET`;403 generic FORBIDDEN;404 existing missing case/report semantics after gate;409 `REPORT_OUTPUT_CHANGED` for report/policy fingerprint changes;409 `REPORT_OUTPUT_SOURCE_INTEGRITY` for existing source row/document case or key mismatches (existing bound-interview source denials/change codes also remain);503 `REPORT_OUTPUT_RENDER_FAILED` rendering/font/dependency failure with no internal path/content details; other unexpected failures controlled500. All successful/error responses no-store via endpoint route handling. A commit/delivery exception may have ambiguous outcome: do not promise every error means no audit was committed. Failures known to occur before commit add no successful export event; after commit the single event remains even if delivery fails. No automatic retries or misleading 'not committed' marker.

Success200 `application/zip`, fixed `Content-Disposition: attachment; filename="report-output.zip"`, Cache-Control:no-store, X-Sha256 lowercase SHA of complete returned ZIP. No server path, credentials or policy body in errors. No persistent temporary renditions. Local library temporary files, if unavoidable, must be owned and removed; do not publish a server retrieval URL.

## 7. Client validation and identity isolation

The UI uses a dedicated bounded STORED-ZIP validator for this exact profile, not merely whole-file SHA and not a generic unzip that silently tolerates extras. Refuse Content-Type other than application/zip, wrong fixed attachment name, missing no-store/X-Sha256, response length over19MiB, or mismatched whole-ZIP SHA before any browser save. A streamed read must enforce the byte cap before accumulating an excessive chunk. Then validate every binary condition in§4, all member budgets and CRCs, and exactly four expected names/order. Do not recursively decompress or execute the opaque DOCX member.

Parse all three JSON members with fatal UTF8, no BOM, duplicate-key rejection, depth64/root1, nonfinite rejection and invalid-surrogate rejection; object shapes and enums are exact (unknown fields rejected). Verify all THREE member sizes/SHA values in manifest against actual preserved bytes, media types, manifest caseId/reportId/outputFormat/language against the originating preview and explicit request, and report.json SHA against expectedReportDigest from that preview. Compare report doc caseId/reportId/version/status/lang with preview caseId/reportId/reportVersion/reportStatus/storedLanguage; a different requested rendering language does not change storedLanguage. Do not parse/stringify report.json to recompute its byte hash.

Verify audit.line SHA over its exact UTF8 string; strictly parse that line and the reason JSON without reserializing the line. Enforce original audit action report.export/category Report/entity_type report/entity_id reportId, positive integer seq (not bool), allowed role equals request role, operator equals request operator, valid UTC/prev hash and existing known line keys. snapshot_ref must point to included snapshot.key; snapshot.auditSeq equals line.seq and audit envelope seq; snapshot IDs/before status/after format/lang/rendered SHA/summary/reason and exact legacy fields must match the request/report and existing append_operation shapes. The canonical reason has exactly the six specified keys and binds report.json SHA, rendered SHA,format/lang,bundle format/version; raw line reason and snapshot reason must be identical. Existing before/after textual summaries follow the known legacy str(dict) format in status and format/lang/sha field order; do not interpret arbitrary free text as a full source document. This verifies only package self-consistency, not authenticated origin or a complete audit chain.

Any missing/invalid/bounded-validation failure yields an UNKNOWN delivery outcome, not successful download and not automatic new generation. The client creates no object URL/save action until all validation succeeds. Each request carries an in-memory generation token bound to case/report, current identity(role/operator), chosen options, and preview digest. On case/report/identity change or unmount, invalidate token, abort where supported and discard any later response without creating an object URL or saving bytes. A stale response must not update another scope's status. Options/preview may not change under a pending request. Persist only unknown-state metadata, never report/ZIP/audit contents; after reload do not invent a recovery endpoint. An explicitly acknowledged new generation rechecks preview and authorization and may create another audit event. A browser save invocation is not proof of durable client storage.

## 8. Synthetic independent acceptance matrix

- Real PDF and DOCX generation separately, exact4 members, parsed text/content, canonical full stored report unchanged even when render language differs; SHA/size/media/type and audit/snapshot links verified.
- Exactly one renderer call and one export event+snapshot per successful HTTP request. No report edits; old ordinary export behavior/schema preserved.
- Default Investigator/all denied categories/field rules, missing/current audit permission, cross-case, current source confidentiality and malformed policy reject before rendering or disclosure.
- Renderer stub opens second database connection and changes report/policy while render is out of transaction: write succeeds; response409 or403, no export audit. Source access changed between phases rechecked. Actual font/PDF tests not replaced by stubs.
- Renderer failure, oversize before/after render, manifest/ZIP overflow, append/snapshot/commit failure: no premature response and rollback as applicable. Simulated error after commit retains exactly one audit event and unknown UI outcome.
- Duplicate/unknown body fields, hostile filenames, nonfinite/Unicode/depth/JSON budgets; unknown formats/languages; no extra member/path injection.
- Existing working-record archive still accepts new existing-shape report.export event; no new business table/file, no new version selected solely for this download. Case export/import retains audit metadata but does NOT recover generated ZIP/PDF bytes.
- UI one explicit format; strict ZIP/JSON/member/audit validation including CRC/offset/EOCD/unknown fields, wrong request/digest/identity, oversized response and malformed audit; late responses after scope/identity changes never save bytes. Unknown network/invalid response state never automatically POSTs again; successful HTTP/ZIP validation still not asserted to prove physical client save.
