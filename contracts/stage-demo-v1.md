# Local synthetic stage demonstration v1

A reproducible demonstration harness, not production software or deployment. It creates three new empty SQLite data directories, starts actual local uvicorn child processes with seed_demo=False, and uses only real HTTP routes. No ORM insertion, TestClient, API interception, real report reading, external URL fetch, LLM, authentication credential, installation or existing user database is used. Supplied fixtures are explicitly fictional with fixed UTC. Reports are existing template output. Calling review APIs is **synthetic scripted simulation of review actions**, not a real investigator's review or factual confirmation. Workflow Confirmed/Published labels are not professional validation.

## Isolation and lifecycle

`tools/stage-demo/run.sh` uses the repository's existing service/.venv Python, never installs dependencies. Default creates a fresh temporary run directory; `--output NEW_PATH` requires that path not exist and creates it exclusively. Existing files/directories/symlinks are rejected, never overwritten or deleted. Each service owns a separate new source/case-restored/knowledge-history data subdirectory. Host is always127.0.0.1, random free port bound before spawn; socket FD is inherited by the child to avoid check-then-bind races. There is no arbitrary URL/port/existing database CLI option. Port acquisition/startup failure aborts rather than attaching to a running service. Only processes started by this run are terminated. Success/failure retains all evidence artifacts, HTTP step log, process logs and DBs. Ctrl-C shuts down owned children. No automatic background persistence/deployment.

Default stops all services after verification. Optional `--hold` keeps the three owned processes running until Ctrl-C solely for local browser inspection; manifest records loopback URLs and process IDs and explicitly notes that URLs stop working after shutdown. This is an interactive foreground session, not a service install. Existing output directories cannot be resumed through this runner. Browser inspection of retained artifacts is a separate explicit operation.

## Actual flow and checks

1. POST case with fictional flag and fixed UTC, POST fictional vessel.
2. Preview/commit synthetic bytes as evidence, then preview/commit fixed UTC CSV first track with explicit source/timeBasis.
3. New unsigned manual interview bound to registered synthetic evidence; GET current digest; append original Q/A with a new request ID.
4. Generate a template report and simulate explicit confirmation for every generated section, preserving reason text identifying the script. Verify final section review states through GET, not just PATCH status.
5. Export1.3 package (working-record envelope2, required for W10 inert history). Empty target restricted preview and commit same case ID. Verify case, vessels, tracks, interview content/report document, source byte digest and restored provenance through APIs. Imported old receipts remain archive-only409; W10 digest/list/identical commit must all return ARCHIVE_HISTORY_ONLY, and separate authorized history downloads must equal the original CSV/report bytes. Save original package and source/destination comparison artifacts. No automatic main merge or deployment.
6. Separate global knowledge Case/Challenge/Method semantics remain original. Create a synthetic candidate, publish through explicitly marked simulated review, withdraw; export whole online knowledge snapshot. Save into third empty knowledge history store; verify exact downloaded archive SHA+bytes, original historical content/snapshot metadata retained, and online card list/internal queues remain empty. History is not activation or publication.

Fail on unexpected status, missing version/content, differing bytes or unexpected rows. No retries of unknown writes with altered request IDs: each generated body/ID stays fixed for its one request, and failure is recorded rather than guessed successful. This runner is bounded small synthetic data, not exhaustive acceptance, legal validation or proof that all MCIS modules are finished. Cases/knowledge history remain separate archives.

## Artifacts

`run.json` records fixed case/vessel IDs, generated evidence/interview/report/knowledge IDs, artifact paths relative to run directory, owned process IDs/loopback URLs and lifecycle state. `steps.jsonl` records method/path/status and response SHA, not credentials. JSON response snapshots, `.mcase`, raw `.json` knowledge archive and original fictional inputs are retained. File digests included in final manifest can be recomputed. Manifest success is written only after all API verification completes. Failure records the failed step/error and services stopped, without claiming completed verification. Browser guide consumes this manifest; its separately recorded screenshots/checks do not alter API test status.

## Re-running on a prepared Linux checkout

Requires the existing service Python environment and its FastAPI/SQLAlchemy/uvicorn dependencies. Browser checks additionally require existing web/node_modules, Node, Playwright Python and an explicitly supplied Chromium executable; no dependencies are downloaded by the harness. Run `bash tools/stage-demo/run.sh --output /absolute/new-output-directory` from the checkout. Add `--hold` for browser inspection; use a second terminal on the same Linux host and PID/network namespace for the browser command in the walkthrough. Python optimization (`-O` or `PYTHONOPTIMIZE`) is rejected because this small test harness uses assertions. This is a verified Linux workflow, not a claim of macOS/Windows support. The backend core command is deliberately unavailable: this demonstrates the selected API/template flow, not physical simulation, LLM or W11.

A normal runner exit retains artifacts and marks services stopped. Abrupt process/namespace termination or machine failure can leave a stale `running:true` manifest; that flag alone is not authority to connect. The browser separately checks exact process command/data directory, process-start ticks and owned listening socket before accessing the service, refusing stale or uncheckable state. It does not resume a stopped run or attach to an unrelated service. This is defensive local tooling, not an adversarial operating-system security boundary.
