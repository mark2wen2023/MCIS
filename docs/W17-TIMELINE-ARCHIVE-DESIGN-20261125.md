现有写入与读取不对称：[导出/旧导入口](../service/mcis_service/package/mcase.py)已经序列化两类分析记录，而[严格导入](../service/mcis_service/package_intake/parser.py)拒绝非空旧成员；旧导入口逐条写文档会丢数据库创建/更新时间。现有工作记录归档会先拒绝有未支持记录的案。**只加表白名单不能恢复完整数据。** 单一登记证据的 v1.2 已通过合成原件往返，不等于复杂案归档。

## 推荐方案（待决定）

1. 第一段只支持 `timeline_events` 与 `timeline_conflicts`。建议新外层版本 1.4.0 与一个清单校验的 `analysis/timeline-archive.v1.json` 配对，工作记录内部 v1 不改。新版本不重复写非空旧时间线成员。外层 1.0–1.3 的合法/拒绝行为与旧字节不变。没有完整验证对象的旧入口拒绝新版本，不默默降级。
2. 独立成员保留同案的原行标识、创建/更新时间、原文档。校验两类正式 Schema，并检查同案、唯一键、已存在的船舶及证据引用、有限数值、时间顺序、当前模拟到 UTC 毫秒口径和容量上限。冲突原状态、草稿、缺失字段不擅自补写；不允许跨案引用或用另一条记录替代原件。
3. 自检与恢复使用同一份严格解析结果。先通过现有归档权限及时间线读取权限，再读相关内容。恢复按已有暂存/事务流程显式保存原时间戳，不覆盖已有案件；失败时核对数据库、证据源、审计与临时文件。
4. 复导必须覆盖已恢复案件：固定[历史包校验器](../service/mcis_service/working_records_archive/validation.py)只接受旧版本。新增版本必须验证嵌套成员与版本配对、保留历史原字节，并沿用深度/字节预算。若历史含新版本而当前无法重建，明示拒绝。首次不支持时间线与 W10 v2 历史共存，不删任何记录换导出成功。
5. 复杂演示案的另外四组（草稿、规则分析、会商、建议）仍不支持；因此完整演示案依然拒绝。跨平台单列：Windows/Unity 的实际读、恢复、复导未验，不称兼容。
