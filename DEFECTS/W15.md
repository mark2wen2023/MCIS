## 缺陷

### W15-D01 公开集合是内部可变实例，调用方强转后可绕过全部结构规则，写出的文件读不回来（一般）
- 位置：`BowTieModel.Elements/Edges`、`AcciMapModel.Nodes/Edges`、`StampModel.*` 返回内部 `List<T>`；`SystemicRefs.*Ids` 返回内部 `string[]`。
- 复现：`W15_D01_ExposedCollections_CannotBypassStructuralRules`
  1. `((IList<SystemicEdge>)bowTie.Edges).Add(new SystemicEdge("C1","T1"))`（后果→威胁）；
  2. `((IList<SystemicEdge>)acciMap.Edges).Add(new SystemicEdge("N5","N0"))`（上行边）；
  3. `((IList<string>)strongNode.Refs.EvidenceIds)[0] = " "`（Strong 去掉证据）；
  4. `bowTie.Elements` 强转后 `RemoveAt(0)` 删掉顶事件。
- 实际：四种篡改都成功。篡改后 `Validate()` 仍然 `IsValid=true`：Validate 不复查方向、环、边种类，Strong 规则只数证据个数（Count）。`ToJson()` 写出文件后，`FromJson` 报 `sys_invalid_edge`，文件读不回来。
- 期望：对外只暴露只读视图（`AsReadOnly()` 或副本），篡改不能影响模型。或者 Validate 复查边合法性和空白证据，保证“Validate 通过的模型一定能往返”。
- 说明：要调用方故意强转才会触发，所以定为一般；但后果是案件文件损坏，建议和 D02 一起修。

### W15-D02 SystemicRefContext 的 HFACS 引用是构造时快照，和证据、建议的实时查询不一致（一般）
- 位置：`SystemicCommon.cs` 中 `SystemicRefContext` 构造器 `_hfacs = new HashSet(hfacs.Findings…)`；证据走 `_ledger.Get(id)`，建议走 `_board.Get(id)`，都是校验时实时查。
- 复现：`W15_D02_HfacsContext_IsLiveQuery_LikeLedgerAndBoard`。先建上下文，再登记证据 EV-002、新增 HFACS 发现 HF-F02，然后校验引用这两项的节点。
- 实际：证据不误报（对照组通过），HFACS 误报 `sys_unknown_hfacs [A] HF-F02`。
- 期望：四类引用语义一致，按校验时刻查询。类注释里写的也是“只读查询”。
- 附带观察：ECFC 已知集合不 Trim，节点引用却会 Trim。已知 ID 带空格（如 `" E1 "`）时会误报 `sys_unknown_ecfc`。实际数据里很少出现，没有单列。

### W15-D03 SystemicDocument 不校验 caseId（一般）
- 位置：`SystemicDocument` 公开构造器和 `FromJson`（`StrOrNull(root,"caseId")`）。
- 复现：`W15_D03_Document_InvalidCaseId_Flagged`，取 `null`、`""`、`"  bad id \n"` 三种值。
- 实际：三种都能建文档，`Validate()` 通过，往返也成功（null 写成 `"caseId":null`）。Evidence 模块的 `EvidenceItem.IsValidCaseId` 认为这三种都非法。
- 期望：systemic.json 要和 .mcase 的案件挂钩，caseId 非法时 `Validate` 应报 `sys_invalid_id`，或者提供返回 `Result<SystemicDocument>` 的工厂方法，和 Evidence 用同一套格式规则。

### W15-D04 屏障状态缺少 Degraded（部分有效）（一般，已知待改，没写失败用例）
- 位置：`BowTie.cs` 的 `enum BarrierState { Effective, Failed, Missing, Unknown }`。
- 依据：原型屏障图例是“失效 / 部分 / 有效”，屏障表里的“VTS 交通组织与警告”和“水密分舱”标的是“部分”。
- 真实案例佐证：海力5 案“落水人员救助与搜救”的结果是 13 人获救、2 人死亡，属于部分有效，现在只能填 Unknown 或 Failed（见 `RealCaseHaili5Tests`）。
- 补齐时要同步改：`BarrierStats` 的键、JSON 枚举名、`SystemicDemoData` 中“部分”的屏障，以及 FromJson 对旧文件的兼容。

## 需要架构师裁定的规格歧义

- **A1 Bow-tie 威胁前因链**：要不要允许威胁→威胁，或者给威胁加“根原因”子节点？真实报告的原因常常是链式的（海力5 案有 4 级）。现在只能压平。
- **A2 AcciMap 上行边**：Svedung & Rasmussen 的 AcciMap 允许由下往上的信息/反馈流，例如险情报告上传、检查发现反馈给公司。现在只允许设备→船员一个例外。要不要加“信息流”边类型（不参与因果环判断）？
- **A3 原型和规格的层名不一致**：原型 AcciMap 的 6 行是“政府/法规、主管机关/VTS、公司/船东、船舶/驾驶台、设备与环境、事件序列”，没有“船员行为”行，多了“事件序列”行；实现按规格分层，事件放在设备与环境层。界面按哪个来？
- **A4 主体/船舶归属**：多船事故的 AcciMap、Bow-tie 节点要不要加 `ActorId`（如 haili5 / wanhai_a17），以便着色和按船过滤？
- **A5 引用类型覆盖**：原型屏障表的“回链”列有 `IR-06`（询问笔录）、`COLREG R6`（W1 条款）、`DamageTrack`。SystemicRefs 只有证据、ECFC、HFACS、建议四类。询问笔录算不算证据 ID？COLREG 条款引用要不要加一类？
- **A6 Moderate 是否要求证据**：W18 HFACS 规定 Strong 和 Moderate 都必须挂证据和 ECFC；W15 只要求 Strong。同一个 `EvidenceStrength` 在两个模块里口径不同，要不要统一？
- **A7 STAMP 孤立控制器**：没有任何控制动作和反馈的控制器，现在 `Validate` 不报；受控过程孤立会报 `sys_isolated_node`，AcciMap 孤立节点也会报。要不要统一？
- **A8 UCA 情境（Context）可以为空**：CAST 的 UCA 按定义包含“在什么情境下不安全”。要不要把 Context 设为必填，至少 Strong 时必填？
- **A9 编辑能力**：三种模型只有 Add/Connect，没有删除节点/边、修改屏障状态或引用的 API。原型是可编辑视图，“从 ECFC 导入节点”按钮也没有对应 API。属于本包还是 UI 包？
- **A10 证据状态**：Strong 结论引用了 ledger 中“需复核”状态的证据，现在只查存在性，不报。要不要提示？
- **A11 JSON 元素顺序依赖**：`elements` 里升级因素必须排在它的屏障之后，否则加载报 `sys_unknown_node`。ToJson 总是按插入顺序写，所以自产文件没问题，但手工编辑或第三方工具写的文件可能失败。要不要先建节点后挂升级因素（两遍加载）？
